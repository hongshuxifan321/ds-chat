## A. 已修：发送前补传历史图片的写放大（2026-11-19，`d6ffe2b`）

**症状**：导入历史后继续提问，点发送表现为长时间假死（大对话 20 秒以上、界面无提示），
部分用户描述为「闪退回初始界面」。

**当时定位**：`src/services/chat/store.ts` 的 `prepareFiles`，导入的图片没有 `serverId`，
发送前逐张补传；每成功一张就 `saveServerIds` → `persist`，把整份会话重写一遍。

**修复**：循环里只收集 `serverId`，循环结束后批量写一次；内联的请求快照刷新抽成 `refreshRequest` 复用。

**复测（IndexedDB 写入计数，150 轮 / 24000 字 / 30 张图）**：

| | `sessions` 写入次数 | 累计耗时 | `sessionSummaries` 次数 |
|---|---|---|---|
| 修复前 | 33 | 47.2 s | 33 |
| 修复后 | 3 | 5.1 s | 3 |

**但端到端没有变快**（点击发送 → `/messages` 请求发出）：

| | 30 张图 | 0 张图 |
|---|---|---|
| 修复前 | 27.4 / 31.8 / 40.4 s | — |
| 修复后 | 34.5 / 43.2 / 44.4 s | 5.0 s |

零图基线 5.0 s，30 张图多出 30～40 s ⇒ **每张图仍有约 1.1～1.3 秒**，这段开销修复前后都存在。

**因此本文件早前的归因不完整**：「每张图重写整份会话」确实存在、也确实被消除了，
但它不是假死的主因 —— 写入从 33 次降到 3 次，端到端耗时却没变。
真正的瓶颈尚未定位，见 C 节。**教训：先量端到端，再归因到某个具体调用。**

**复现**：`probe_write_amp.py 150 24000 30`（见文末脚本表）。

## B. 已修：无可读会话的归档会清空历史（2026-11-19，`3dd4452`）

**症状**：导入一份「索引里列了会话、会话正文却读不出来」的归档，旧版会报「已导入 0 个对话」，
并把本地原有历史全部清掉 —— 静默数据丢失。

**定位**：`importArchive` 只校验了「导入成功的都在索引里」，没校验「索引里的一个都没导进来」。

**修复**：`imported.size === 0 && (total > 0 || listed.size > 0)` 时报 `backupIncomplete`，
发生在替换正式数据之前。

**复测**（`probe_import_guard.py`，先导入 3 条正常会话，再导入坏包）：

| | 界面提示 | 原有 3 条会话 |
|---|---|---|
| 修复前 | 已导入 0 个对话 | **全部消失** |
| 修复后 | 文件内容不完整，无法导入 | 一条不少 |

**注意**：判定偏保守 —— 归档里的会话全部解析失败时会整包拒绝，而不是「导入 0 条」。
这是安全方向（宁可拒绝，不要清空），但用户可能不理解为什么被拒，提示语可再打磨。

## C. 未修：导入历史后发送仍然很慢（约 1.1～1.3 秒 / 张）

A 节修掉了写入放大，端到端没变。现状：150 轮 / 30 张图的会话点发送，要 34～44 秒才发出请求；
零图同规模只要 5 秒。每多一张历史图片稳定增加约 1.1～1.3 秒。

**尚未证实的候选原因**（按可疑度排）：

1. 每张图补传都会更新上传任务状态，带动长列表重渲染（150 条长消息的 Markdown 重解析）；
2. 上传本身串行排队（`enqueueUpload`），一张等一张；
3. 手机上 IndexedDB 与图片 base64 兜底会进一步放大。

**原修法建议里已完成 1 条，剩 3 条**：

1. ~~补传成功后批量写一次~~（已完成，见 A）
2. 只同步补传最近两轮的图，更早的等请求发出后后台补，下一轮才进上下文
3. 补传期间在 pending 气泡里显示进度 —— **成本最低，建议先做**，让等待看得见
4. `activeId` 写进 URL hash（`replaceState`），刷新或被系统杀掉后回到原对话

**复现**：`probe_write_amp.py <轮数> <字数> <图片数>` 同时给出端到端耗时与 IDB 写入计数。

## D. 未修：`activeId` 不持久化，也没有 error boundary

`activeId` 只存在内存里，所以任何一次页面重载（刷新、崩溃、系统回收标签页、切走太久被丢弃）
都回到欢迎页，用户看到的就是「闪退」。渲染异常同样没有兜底，会直接白屏。

修法：`activeId` 用 `replaceState` 写进 URL hash，启动时按 hash 恢复；外层加一个 error boundary，
至少给出「刷新 / 导出备份」的出路。这条独立于 C，可以先做。

## E. 已修：刚发送的附件当轮显示成文件卡片（2026-11-20）

发一条带图片的消息，当轮消息里那张图会先渲染成文件卡片（名字 + 大小），刷新并重新打开会话才变缩略图。

原因：`useFileView` 只在挂载时读一次 IndexedDB，而发送是「先渲染消息 → 再异步 `persist()` 写原件」，
首帧读不到就落进 `url === null` 的分支，且不会重试。合入上游前后表现一致（线上旧版与合并版实测都是
发送后 `document.querySelectorAll('img')` 为空、刷新后才有 `blob:` 缩略图），属于既有问题。

修法（`src/components/files/useFileView.ts`）：原件是 IndexedDB ID 时，读不到就按 60 / 160 / 400 ms
重试三次，读到即用；原件确实丢了（存储被清、导入漏图）在一次重试链后仍然退回文件卡片，不会空转。
草稿传的是 `File`，不走重试。

实测（`probe_attach_firstframe.py`）：修复后发送后 **0.15 s** 内出现 `blob:` 缩略图；同一脚本对着
修复前的线上版本跑 4.1 s 仍没有缩略图。删掉原件后刷新重开稳定停在文件卡片，不会一直空占位。

## G. 部分已修：依赖告警（katex 那条上游仍未修，CSP 是补偿控制）

**2026-11-20 首次排查**：`npm audit --omit=dev` 报 10 条（8 high / 2 low），全部 `fixAvailable: false`：
katex 0.16.22 原型污染可绕过 trust（GHSA-238p-pmpm-9mq7）；mermaid 11.10.1 六条 moderate（classDef /
配置注入导致 CSS 与 HTML 注入、Gantt / XY / radar 无限循环 DoS、原型污染）；lodash-es（mermaid 传递）
`_.template` 代码注入（GHSA-r5fr-rjxr-66jc）与 `_.unset` 等原型污染。

**同日合并 Dependabot 两个 PR 后**（`5473330` mermaid 11.10.1→11.16.1、`6f0afe4` katex 0.16.22→0.18.2）：

- `npm audit --omit=dev` → **10 条变 3 条，high 清零**（`{"low":3,"high":0}`）
- lodash-es 实际解析到 **4.18.1**：mermaid 11.16.1 把锁文件里所有 `lodash-es@4.17.21` 换成了 4.18.1，
  那条 `_.template` 代码注入（high）随之消失。这也是 Dependabot 单独修不掉的那条——它对 lodash-es
  报过两次 `security_update_not_possible`（latest-resolvable 4.17.21 / lowest-non-vulnerable 4.18.1），
  因为父包把版本钉死了
- **katex 那条 low 在 0.18.2 里依然存在**（上游还没发补丁），升级 katex 的收益只是不再落后两个 minor，
  不是这条告警的修复
- 剩下 3 条 low：katex、mermaid（传递）、micromark-extension-llm-math（katex 传递）

判断与之前一致：攻击面真实（这两个库直接渲染模型输出），但**利用链最后一环都要执行脚本**——
`javascript:` 地址或模板编译出的函数——而页面的 CSP（`script-src 'self'`，无 `'unsafe-inline'` /
`'unsafe-eval'`）会拦住。升级前后的注入实测见 `swtest/probe_math_mermaid_security.py`：模型输出里夹带
`javascript:` 链接、`\href`、Mermaid 里的 `<img onerror>` 与 `<script>`，页面均未产生危险链接、未执行脚本。

跟进方式：Dependabot 告警与自动安全更新已打开（2026-11-20），有补丁会自动开 PR；手动复查用
`npm audit --omit=dev`。**tinypool 那条会长期报红**：它是 vitest 的开发依赖（不进线上包），父包钉死
2.1.0 而修复版 2.1.2 未发布，Dependabot 每次都会 `security_update_not_possible`，属噪音。
