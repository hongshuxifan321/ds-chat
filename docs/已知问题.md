## 1. 导入历史后继续聊，点发送「闪退」回初始页（最高优先级，未修）

### 症状

用户导入官方导出的历史对话后，选中某条会话继续提问，点发送就回到欢迎页，看起来像闪退。
有两位用户反馈，发生时上下文用量分别是 41% 和 70%。

### 已经排除的方向

把导入流程整条真跑了一遍（真 ZIP → 设置页上传 → 确认覆盖 → 选会话 → 输入 → 发送），覆盖 4 种形态：

- 普通多轮：含思考、搜索、阅读链接、图片附件
- 末条回答还是 WIP
- 上一条回答失败（模板红字）
- 带分支：重新生成过、编辑过提问、当前停在树中间

桌面 1440 与手机 390 都发得出去：`pageerror` 零、console 零、URL 不变、`activeId` 不变。
**问题不在消息树、上下文拼装、请求构造，也不在导入后的数据形态。**

### 定位

`src/services/chat/store.ts` 的 `prepareFiles`：导入的图片没有 `serverId`，发送前要逐张补传；
而每成功一张就 `saveServerIds` → `persist`，把**整份会话重写一遍**。

| 会话规模 | 0 张图 | 30 张图 | 每张成本 |
|---|---|---|---|
| 30 轮 / 72 万字 / 0.7 MB | 0.8 s | 3.6 s | ≈ 0.09 s |
| 150 轮 / 360 万字 / 3.6 MB | 2.0 s | 19.2 s | ≈ 0.57 s |

上传本身被 mock 掉了，所以这些时间基本全是本地开销。
成本随会话体积线性上涨，正是「每张图重写整份会话」的特征。
这期间回复气泡是空 pending，界面没有任何进度提示。

### 为什么看起来像「闪退」

41%～70% 的对话通常 3～10 MB、几十张截图，光这一步就要 20～60 秒假死。
手机上 IndexedDB 更慢，图片还可能存成 base64，被系统判定卡死就会回收标签页。
重开自然落在欢迎页 —— `activeId` 不持久化，也没有 error boundary，**任何 reload 都回到 Welcome**。
数据本身没丢。

这条推断没有真机日志证实。要证实的办法：看用户侧是否有标签页被回收的迹象，或加临时计时埋点。

### 修法建议

按性价比排序，建议分两批做：

1. 补传成功后批量写一次（现在 N 张图 = N 次整会话写 → 1 次）
2. 只同步补传最近两轮的图，更早的等请求发出后后台补，下一轮才进上下文
3. 补传期间在 pending 气泡里显示进度
4. `activeId` 写进 URL hash（`replaceState`），刷新或被系统杀掉后回到原对话

第 1 条是根因（写入放大），第 4 条是独立的体验兜底，可以分开做；第 3 条成本最低，先让假死「看得见」。

### 怎么复现

需要一份真 ZIP 归档（官方导出格式见 `src/services/chat/history/README.md`）。
导入后 mock 掉 `/files`（返回假的 file id）和 `/messages`（假 SSE），
测「点发送 → 出首字」的耗时，对比有图/无图、大会话/小会话。

本机有现成脚本，在仓库外的 `~/.dsh/workspaces/swtest/`（Playwright + mock SSE）：
`repro_import_send.py`（小归档三种形态）、`repro_branch_import.py`（分支 + 停在中间）、
`repro_mobile_send.py`（手机视口）、`repro_big_import.py <轮数> <字数> <图片数>`（量级实验）。

## 2. `activeId` 不持久化，也没有 error boundary

`activeId` 只存在内存里，所以任何一次页面重载（刷新、崩溃、系统回收标签页、切走太久被丢弃）
都回到欢迎页，用户看到的就是「闪退」。渲染异常同样没有兜底，会直接白屏。

修法：`activeId` 用 `replaceState` 写进 URL hash，启动时按 hash 恢复；外层加一个 error boundary，
至少给出「刷新 / 导出备份」的出路。这条独立于问题 1，可以先做。
