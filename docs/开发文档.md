## 1. 定位与目标

一个**自带 API Key 的 DeepSeek 对话客户端**，纯静态、无后端、可安装为 PWA。
用户被官方限额逼出来时，给他一个"零学习成本 + 自己付费 + 数据在本地"的出口。

一句话：**官方 App 的付费逃生舱。**

**目标**

- 1:1 还原官方网页端的对话体验（外观、交互、能力）
- 一键导入官方导出的历史对话
- 用户填自己的 Key，数据只存在浏览器本地
- 可安装到桌面/手机主屏，装完后离线可用
- 零服务器成本、零运维

**非目标**

- 不做后端、不做账号体系、不做云同步
- 不做代充、不做共享 Key、不做反代（违规且必挂）
- 不做内容审核（BYOK 模式，服务由 DeepSeek 提供）
- 不做国内备案、不上应用商店

## 3. 架构与运行环境

```
浏览器（PWA）
├── 静态资源 ← GitHub Pages（HTTPS）
│   ├── index.html / static/js / static/css
│   ├── manifest.json
│   └── sw.js（service worker）
├── localStorage ← API Key、设置
├── IndexedDB ← 会话、消息分支、附件原件
└── 直连 https://api.deepseek.com/anthropic/v1/messages
        （实测：`127.0.0.1:5750`、`localhost:8090`、`192.168.3.57:8090`、`https://hongshuxifan321.github.io/ds-chat/` 均被回显允许）
```

**Service Worker 策略**

| 请求类型 | 策略 |
|---|---|
| 页面导航 | network-first，失败回退缓存的 index.html |
| 同源静态资源 | cache-first，命中即用 |
| 跨域 API 请求 | **完全不拦截**，绝不写进缓存 |
| 公告与教程（`/notice/`） | network-first，请求带 `cache: no-cache` 绕过 HTTP 缓存，失败回退上次缓存；排在导航分支之前，避免下载的 PDF 被当成 index.html 存进缓存 |

**跨域已实测**：以 Pages 站点为 origin 向 `api.deepseek.com` 发 CORS 预检，返回 200 并回显该 origin，
允许 `authorization, content-type, x-api-key, anthropic-version, anthropic-beta`——线上不会被跨域拦下。

### 部署流程

1. 在 GitHub 创建公开仓库 `ds-chat`（不初始化 README）
2. **先启用 Pages**：仓库 → Settings → Pages → Source 选 **GitHub Actions**
   顺序不能颠倒：工作流里的 `actions/configure-pages` 默认不代为启用站点（`enablement` 默认 `false`），
   仓库尚未启用 Pages 时该步骤会失败，首次 Actions 白跑一轮。
3. 关联远端并推送
   ```sh
   git remote add mine https://github.com/hongshuxifan321/ds-chat.git
   git push -u mine pwa:main
   ```
4. 等 Actions 跑完（约 2–3 分钟）
5. 访问 `https://hongshuxifan321.github.io/ds-chat/`
6. 设置里填自己的 Key，跑一轮对话验证

CI 会依次执行：`pnpm install --frozen-lockfile` → `pnpm type` → `pnpm lint` → `pnpm build` → 上传 `dist` → 部署。
本地已预跑通过：tsc 0 error、oxlint 0 warning、构建成功；lockfile 的 28 条依赖声明与 `package.json` 静态比对一致。`pnpm install --frozen-lockfile` 未能在本机复现（pnpm store 锁被拒），CI 首跑结果以 Actions 日志为准。

### 部署时踩过的坑

1. **仓库必须是完整历史。** 本地这份曾是浅克隆（`.git/shallow` 钉在上游 `5d5dd75`），直接推空仓库会报
   `did not receive expected object …`——`git fsck` 与 `git bundle verify` 在浅边界内都显示「完整」，查不出来。
   解法：`git fetch --unshallow origin` 补全上游历史后再推。
2. **构建会压缩 `public/sw.js`**（源 1690 字节 → 产物 887 字节），逐条比对过语义等价：跨域请求仍完全不拦截、
   导航仍 network-first、静态资源仍 cache-first。
3. **CI 产物与本地构建的 hash 不同**（CI 按 `pnpm-lock.yaml`、本地可能用别的安装方式），所以验收以部署后的站点为准，不看 bundle hash。

### A. 已修：发送前补传历史图片的写放大（2026-11-19，`d6ffe2b`）

**症状**：导入历史后继续提问，点发送表现为长时间假死（大对话 20 秒以上、界面无提示），
部分用户描述为「闪退回初始界面」。

**当时定位**：`src/services/chat/store.ts` 的 `prepareFiles`，导入的图片没有 `serverId`，
发送前逐张补传；每成功一张就 `saveServerIds` → `persist`，把整份会话重写一遍。

**修复**：循环里只收集 `serverId`，循环结束后批量写一次；内联的请求快照刷新抽成 `refreshRequest` 复用。

**复测（IndexedDB 写入计数，150 轮 / 24000 字 / 30 张图）**：

| | `sessions` 写入次数 | 累计耗时 | `sessionSummaries` 次数 |
|---|---|---|---|
| 修复前 | 33 | 47.2 s | 33 |
| 修复后 | 3 | 5.1 s | 3 |

**但端到端没有变快**（点击发送 → `/messages` 请求发出）：

| | 30 张图 | 0 张图 |
|---|---|---|
| 修复前 | 27.4 / 31.8 / 40.4 s | — |
| 修复后 | 34.5 / 43.2 / 44.4 s | 5.0 s |

零图基线 5.0 s，30 张图多出 30～40 s ⇒ **每张图仍有约 1.1～1.3 秒**，这段开销修复前后都存在。

**因此本文件早前的归因不完整**：「每张图重写整份会话」确实存在、也确实被消除了，
但它不是假死的主因 —— 写入从 33 次降到 3 次，端到端耗时却没变。
真正的瓶颈尚未定位，见 C 节。**教训：先量端到端，再归因到某个具体调用。**

**复现**：`probe_write_amp.py 150 24000 30`（见文末脚本表）。

### B. 已修：无可读会话的归档会清空历史（2026-11-19，`3dd4452`）

**症状**：导入一份「索引里列了会话、会话正文却读不出来」的归档，旧版会报「已导入 0 个对话」，
并把本地原有历史全部清掉 —— 静默数据丢失。

**定位**：`importArchive` 只校验了「导入成功的都在索引里」，没校验「索引里的一个都没导进来」。

**修复**：`imported.size === 0 && (total > 0 || listed.size > 0)` 时报 `backupIncomplete`，
发生在替换正式数据之前。

**复测**（`probe_import_guard.py`，先导入 3 条正常会话，再导入坏包）：

| | 界面提示 | 原有 3 条会话 |
|---|---|---|
| 修复前 | 已导入 0 个对话 | **全部消失** |
| 修复后 | 文件内容不完整，无法导入 | 一条不少 |

**注意**：判定偏保守 —— 归档里的会话全部解析失败时会整包拒绝，而不是「导入 0 条」。
这是安全方向（宁可拒绝，不要清空），但用户可能不理解为什么被拒，提示语可再打磨。

### C. 已修：导入历史后发送很慢（39.0 s → 3.1 s，150 轮 / 30 图）

A 节修掉了写入放大，端到端没变。修前现状：150 轮 / 30 张图的会话点发送，要 34～44 秒才发出请求。
每多一张历史图片稳定增加约 1.1～1.3 秒。

**根因（2026-11-21 实测，两条都被排除后剩下的那条）**：

- 不是存储：同一个大库里裸读 `files` 记录，30 条 70 字节的 blob，**平均 0.1 ms / 合计 4 ms**
  （`swtest/probe_c_idb_read.py`）
- 不是网络：mock 下单次上传请求 **1～2 ms**
- 是渲染：CDP CPU 采样 30.2 秒里 **28.8 秒落在 `(program)`**（浏览器内部的样式/布局/绘制，不是 JS），
  且「相邻两次上传的间隔」随会话体积增长（60 轮时 208 ms，150 轮时 1.2～3.7 秒）。
  机制：每补传一张图都会 `setTask` 发布一次上传状态，长会话列表（906 条消息、每条 24000 字 markdown）
  跟着重渲染并重排

**修法**：`attachments.ts` 新增 `runWithoutUploadProgress()`，历史补传整段包在里面，
期间任务状态先挂起、结束时一次性发布（`store.ts` 的 `prepareFiles`）。每张图的上传结果照样经
`updateServerIds` 写回会话，只是不再逐张触发界面更新。

**数据**（同一口径 `probe_write_amp.py 150 24000 30`，点发送到请求发出）：

| | 修前 | 修后 |
|---|---|---|
| 端到端 | 39.0 s（另一次 40.2 s） | **3.1 s** |

修后剩的 3.1 秒主要是三次会话落盘（906 条消息，单次最大 2.5 s），属保存链路，不再是补传。
配套断言：`swtest/probe_c_backfill.py`（请求里 image 块 6 / 不同 file_id 6 / 上传 6 次，不重复）。

**没做的两件**（理由留档）：

1. 并发补传：批量发布后每张只要 ~0.1 s，为这点收益把串行循环改并发不划算
2. pending 气泡进度：同样因为已经不再慢；真要继续压，该压的是那三次整份会话落盘

~~只同步补传最近两轮~~ 仍然不做：会让早期图片悄悄掉出上下文，模型看到的输入变了，不是纯性能改动。

### D. 已修：`activeId` 持久化 + error boundary（2026-11-21）

修前：`activeId` 只存在内存里，任何一次页面重载（刷新、崩溃、系统回收标签页、切走太久被丢弃）
都回到欢迎页，用户看到的就是「闪退」；渲染异常也没有兜底，直接白屏。

修法：

- 会话深链 `#/s/<id>`（`services/chat/sessionUrl.ts`）：`selectSession` / 新建会话 / 新对话 /
  删除当前会话 / 替换历史五处同步写或清 `replaceState` 的 hash（不新增历史记录，后退键行为不变）；
  `initChat` 读到列表后按 hash 恢复，id 不在列表里就清掉，不留死链
- 根节点包 `ErrorBoundary`（`app/ErrorBoundary.tsx`）：兜底页给「刷新页面」「导出备份」两条出路，
  错误细节只进 console

验证：`swtest/probe_deeplink.py` 10 项全 PASS（写 hash、刷新恢复、带 hash 直接打开、新对话清空、
死链清理、删除当前会话清空、无页面异常）；崩溃兜底用**临时注入 throw 的构建**验过一次
（标题/两个按钮/主界面未渲染），验完已回滚，dist 里搜不到注入代码。

注意：同一个 URL 只改 hash 的 `page.goto()` 属同文档导航，应用不会重新初始化——
写这类探针必须新开页面，否则会误判成「深链没生效」（这次踩过）。

### E. 已修：刚发送的附件当轮显示成文件卡片（2026-11-20）

发一条带图片的消息，当轮消息里那张图会先渲染成文件卡片（名字 + 大小），刷新并重新打开会话才变缩略图。

原因：`useFileView` 只在挂载时读一次 IndexedDB，而发送是「先渲染消息 → 再异步 `persist()` 写原件」，
首帧读不到就落进 `url === null` 的分支，且不会重试。合入上游前后表现一致（线上旧版与合并版实测都是
发送后 `document.querySelectorAll('img')` 为空、刷新后才有 `blob:` 缩略图），属于既有问题。

修法（`src/components/files/useFileView.ts`）：原件是 IndexedDB ID 时，读不到就按 60 / 160 / 400 ms
重试三次，读到即用；原件确实丢了（存储被清、导入漏图）在一次重试链后仍然退回文件卡片，不会空转。
草稿传的是 `File`，不走重试。

实测（`probe_attach_firstframe.py`）：修复后发送后 **0.15 s** 内出现 `blob:` 缩略图；同一脚本对着
修复前的线上版本跑 4.1 s 仍没有缩略图。删掉原件后刷新重开稳定停在文件卡片，不会一直空占位。

### H. 已修：引用角标插进代码围栏（2026-11-21，`cd14630`）

**2026-11-20 发现，次日修复。**

带联网引用的回答会在正文末尾插 `[citation:N]`（`src/services/chat/view.ts:173-178`：先 `trimEnd()`
再拼角标，最后把尾部空白补回来）。若正文最后一行正好是代码围栏的闭合行，角标就贴到围栏上：

````
...分支二
```[citation:1]      ← 不再是合法闭合行
````

后果：**该代码块永不闭合**，把后面的内容全吞进 code，角标本身也丢失。实测抓到的应用内输入是
`"mindmap\n  root((中心))\n    分支一\n    分支二\n```[citation:1]"`，mermaid 报
`There can be only one root. No parent could be found for ("citation:1")`。

定位时排除的两个方向（留档，免得下次重走）：

- 同一段代码用 mermaid 官方 dist 直接渲染 8 种图表类型全部正常 → **不是 mermaid 的问题**
- 线上版本（mermaid 11.16.1）与本地升级后（12.3.0）表现一致 → **不是依赖升级引入的**
- 影响面：联网 + 代码回答（很常见）时，最后一个代码块的内容里多一条 ` ```[citation:1] `，
  复制代码、导出网页、代码块显示全被污染

**修法**：`joinTextBlocks` 插角标前先判断块尾最后一行是否围栏行
（`/(?:^|\n)[ \t]*(?:`{3,}|~{3,})[^\n]*$/`），是就先补一个换行，让角标落到围栏外；
代价仅是该边界情况下角标单独成行，其它情况行为不变。

**回归**：`swtest/probe_citation_fence.py`（两种结尾：python 围栏 / mermaid 围栏）。修复后代码内容干净
（`'def add(a, b):\n    return a + b'`）、角标存在（`cite=1`）、mindmap 正常出图（`svg=1` 且无失败状态）；
`probe_mermaid_types` 8/8、`probe_csp` 仍 PASS。

注意：`swtest/probe_mermaid_types.py` 的样例末尾特意留了一段普通正文——如果拿它验证这次的 bug，
末尾必须是围栏，否则踩不到。

### I. 未修：公式观感「长条、字变大、不换行」（2026-11-21 记录，暂不动代码）

**用户原话**（应用用户转述，其中「老师」是对方对维护者的尊称）：
*「这个界面是不是不能渲染 LaTeX 呀？输出是长条，字体变大不会换行的样子捏」*

**没有留存截图**，因此无法确认对方那一屏的具体样子；以下全部是本机实测到的现象，
不是对这条反馈的复现。

#### 结论先行

**公式是渲染的，不是渲染失败。** 线上 `5ef0e0e` 实测（Playwright + 真实 Chrome）：

| 检查项 | 桌面 1440px | 手机 390px |
|---|---|---|
| KaTeX 样式表生效（`.katex-mathml` 的 `position` 为 `absolute`） | ✅ | ✅ |
| KaTeX 字体加载（`document.fonts.check('16px KaTeX_Main')`） | ✅ | ✅ |
| 正文里漏出反斜杠源码 | 0 处 | 0 处 |
| 整页被撑出横向滚动（`documentElement.scrollWidth`） | 否（1440/1440） | 否（390/390） |
| 超长块公式 | 内容 921px / 容器 752px | 内容 921px / 容器 350px |

#### 「长条、字变大、不换行」的三个真实来源

1. **块公式不会折行，容器也看不出还能滚动。** KaTeX 的公式是一个整体，没有断行点；
   `.ds-markdown-math.katex-display`（`src/components/markdown/markdown.css:223-230`）虽有
   `overflow-x: auto`，但滚动条在 Chrome/Safari 上默认隐藏、右侧也没有渐隐提示，
   于是超宽公式看上去就是**被右边缘硬切掉一截**。手机 390px 下尤其明显。
2. **公式确实比正文大一号。** `katex/dist/katex.min.css` 把 `.katex` 设为 `font-size: 1.21em`，
   正文 16px → 公式 19.4px。窄屏上一行又大又长的公式，正是用户描述的「字体变大不会换行」。
3. **矩阵/多列表这类结构天生超宽。** 14 列矩阵实测内容 921px，390px 手机上只能看到前 9 列
   （`swtest/shots/latex_wide_mobile.png`），且左右都没有提示。

#### 顺带实测到的两个真问题（与用户原话未必相关）

- **只有 3 类写法会让 KaTeX 抛错、回退成原始源码**（`src/components/markdown/MathFormula.tsx:43-45`
  走 fallback，把源码原样当正文显示）：`\label{}`、`\require{}`、`\hline` 用在 array 环境之外。
  Node 里用同一版 katex 0.18.2 逐条跑 32 个常见写法，只有这 3 条（外加把 `$` 当公式内容喂进去的
  1 条测试用例本身写错）报错；`\begin{equation}`、`\begin{align}`、`\bm`、`\tag`、`\text{中文}`、
  `\begin{cases}`、`\substack`、`\underbrace` 等在 0.18.2 里都能正常渲染。
  若后续确认用户看到的是「带反斜杠的原文」，就是这一类——修法是回退前先剔除 `\label`/`\require` 再试。
- **单美元会把货币吞掉**：`价格 $5 和 $10 不是公式` 渲染成「价格 `5 和` 10 不是公式」，
  两个 `$` 被当成定界符（`src/services/markdown/parse.ts:42` 的 `singleDollarTextMath: true`）。
  这是官方网页端同款行为，改动它属于产品决策，不是 bug。

#### 2026-11-21 补充：字号三档上线后的影响

设置「通用」页新增正文字号（默认 16 / 加大 1 18 / 加大 2 20），`.katex` 是 `1.21em`，所以公式跟着放大：
默认 19.4px → 加大 2 的 24.2px。同样一条长公式在加大 2 下溢出更多。这是用户知情后接受的取舍
（`08f89bf`），不在本次修复范围内；真要治仍是上面的 A/B/C/D 四个方向。

#### 复现

```powershell
# 渲染链路体检（含样式是否生效、字体是否加载、源码是否泄漏、溢出尺寸）
python probe_latex.py https://hongshuxifan321.github.io/ds-chat/
# 超宽公式 / 矩阵 / 长表格是否撑破整页
python probe_latex_wide.py
# 逐条 LaTeX 写法（探针的段落切分不可靠，判定以 Node 侧为准）
python probe_latex_edges.py [APP_URL]
```

`probe_latex_edges.py` 的结论不可直接采信：它按 `.ds-markdown > *` 切段，而 `$$` 必须位于行首
才是块公式，用例之间会粘连；且 `textContent` 会带出 KaTeX 的 `<annotation>` 原始源码，
看起来像「源码泄漏」其实是隐藏的 MathML。判定抛不抛错要用 Node 直接 `renderToString`。
