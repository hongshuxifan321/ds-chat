## 1. 定位与目标

一个**自带 API Key 的 DeepSeek 对话客户端**，纯静态、无后端、可安装为 PWA。
用户被官方限额逼出来时，给他一个"零学习成本 + 自己付费 + 数据在本地"的出口。

一句话：**官方 App 的付费逃生舱。**

**目标**

- 1:1 还原官方网页端的对话体验（外观、交互、能力）
- 一键导入官方导出的历史对话
- 用户填自己的 Key，数据只存在浏览器本地
- 可安装到桌面/手机主屏，装完后离线可用
- 零服务器成本、零运维

**非目标**

- 不做后端、不做账号体系、不做云同步
- 不做代充、不做共享 Key、不做反代（违规且必挂）
- 不做内容审核（BYOK 模式，服务由 DeepSeek 提供）
- 不做国内备案、不上应用商店

## 3. 架构与运行环境

```
浏览器（PWA）
├── 静态资源 ← GitHub Pages（HTTPS）
│   ├── index.html / static/js / static/css
│   ├── manifest.json
│   └── sw.js（service worker）
├── localStorage ← API Key、设置
├── IndexedDB ← 会话、消息分支、附件原件
└── 直连 https://api.deepseek.com/anthropic/v1/messages
        （实测：`127.0.0.1:5750`、`localhost:8090`、`192.168.3.57:8090`、`https://hongshuxifan321.github.io/ds-chat/` 均被回显允许）
```

**Service Worker 策略**

| 请求类型 | 策略 |
|---|---|
| 页面导航 | network-first，失败回退缓存的 index.html |
| 同源静态资源 | cache-first，命中即用 |
| 跨域 API 请求 | **完全不拦截**，绝不写进缓存 |
| 公告与教程（`/notice/`） | network-first，请求带 `cache: no-cache` 绕过 HTTP 缓存，失败回退上次缓存；排在导航分支之前，避免下载的 PDF 被当成 index.html 存进缓存 |

**跨域已实测**：以 Pages 站点为 origin 向 `api.deepseek.com` 发 CORS 预检，返回 200 并回显该 origin，
允许 `authorization, content-type, x-api-key, anthropic-version, anthropic-beta`——线上不会被跨域拦下。

### 部署流程

1. 在 GitHub 创建公开仓库 `ds-chat`（不初始化 README）
2. **先启用 Pages**：仓库 → Settings → Pages → Source 选 **GitHub Actions**
   顺序不能颠倒：工作流里的 `actions/configure-pages` 默认不代为启用站点（`enablement` 默认 `false`），
   仓库尚未启用 Pages 时该步骤会失败，首次 Actions 白跑一轮。
3. 关联远端并推送
   ```sh
   git remote add mine https://github.com/hongshuxifan321/ds-chat.git
   git push -u mine pwa:main
   ```
4. 等 Actions 跑完（约 2–3 分钟）
5. 访问 `https://hongshuxifan321.github.io/ds-chat/`
6. 设置里填自己的 Key，跑一轮对话验证

CI 会依次执行：`pnpm install --frozen-lockfile` → `pnpm type` → `pnpm lint` → `pnpm build` → 上传 `dist` → 部署。
本地已预跑通过：tsc 0 error、oxlint 0 warning、构建成功；lockfile 的 28 条依赖声明与 `package.json` 静态比对一致。`pnpm install --frozen-lockfile` 未能在本机复现（pnpm store 锁被拒），CI 首跑结果以 Actions 日志为准。

### 部署时踩过的坑

1. **仓库必须是完整历史。** 本地这份曾是浅克隆（`.git/shallow` 钉在上游 `5d5dd75`），直接推空仓库会报
   `did not receive expected object …`——`git fsck` 与 `git bundle verify` 在浅边界内都显示「完整」，查不出来。
   解法：`git fetch --unshallow origin` 补全上游历史后再推。
2. **构建会压缩 `public/sw.js`**（源 1690 字节 → 产物 887 字节），逐条比对过语义等价：跨域请求仍完全不拦截、
   导航仍 network-first、静态资源仍 cache-first。
3. **CI 产物与本地构建的 hash 不同**（CI 按 `pnpm-lock.yaml`、本地可能用别的安装方式），所以验收以部署后的站点为准，不看 bundle hash。

### A. 已修：发送前补传历史图片的写放大（2026-11-19，`d6ffe2b`）

**症状**：导入历史后继续提问，点发送表现为长时间假死（大对话 20 秒以上、界面无提示），
部分用户描述为「闪退回初始界面」。

**当时定位**：`src/services/chat/store.ts` 的 `prepareFiles`，导入的图片没有 `serverId`，
发送前逐张补传；每成功一张就 `saveServerIds` → `persist`，把整份会话重写一遍。

**修复**：循环里只收集 `serverId`，循环结束后批量写一次；内联的请求快照刷新抽成 `refreshRequest` 复用。

**复测（IndexedDB 写入计数，150 轮 / 24000 字 / 30 张图）**：

| | `sessions` 写入次数 | 累计耗时 | `sessionSummaries` 次数 |
|---|---|---|---|
| 修复前 | 33 | 47.2 s | 33 |
| 修复后 | 3 | 5.1 s | 3 |

**但端到端没有变快**（点击发送 → `/messages` 请求发出）：

| | 30 张图 | 0 张图 |
|---|---|---|
| 修复前 | 27.4 / 31.8 / 40.4 s | — |
| 修复后 | 34.5 / 43.2 / 44.4 s | 5.0 s |

零图基线 5.0 s，30 张图多出 30～40 s ⇒ **每张图仍有约 1.1～1.3 秒**，这段开销修复前后都存在。

**因此本文件早前的归因不完整**：「每张图重写整份会话」确实存在、也确实被消除了，
但它不是假死的主因 —— 写入从 33 次降到 3 次，端到端耗时却没变。
真正的瓶颈尚未定位，见 C 节。**教训：先量端到端，再归因到某个具体调用。**

**复现**：`probe_write_amp.py 150 24000 30`（见文末脚本表）。

### B. 已修：无可读会话的归档会清空历史（2026-11-19，`3dd4452`）

**症状**：导入一份「索引里列了会话、会话正文却读不出来」的归档，旧版会报「已导入 0 个对话」，
并把本地原有历史全部清掉 —— 静默数据丢失。

**定位**：`importArchive` 只校验了「导入成功的都在索引里」，没校验「索引里的一个都没导进来」。

**修复**：`imported.size === 0 && (total > 0 || listed.size > 0)` 时报 `backupIncomplete`，
发生在替换正式数据之前。

**复测**（`probe_import_guard.py`，先导入 3 条正常会话，再导入坏包）：

| | 界面提示 | 原有 3 条会话 |
|---|---|---|
| 修复前 | 已导入 0 个对话 | **全部消失** |
| 修复后 | 文件内容不完整，无法导入 | 一条不少 |

**注意**：判定偏保守 —— 归档里的会话全部解析失败时会整包拒绝，而不是「导入 0 条」。
这是安全方向（宁可拒绝，不要清空），但用户可能不理解为什么被拒，提示语可再打磨。

### E. 已修：刚发送的附件当轮显示成文件卡片（2026-11-20）

#### 结论先行

**公式是渲染的，不是渲染失败。** 线上 `5ef0e0e` 实测（Playwright + 真实 Chrome）：

| 检查项 | 桌面 1440px | 手机 390px |
|---|---|---|
| KaTeX 样式表生效（`.katex-mathml` 的 `position` 为 `absolute`） | ✅ | ✅ |
| KaTeX 字体加载（`document.fonts.check('16px KaTeX_Main')`） | ✅ | ✅ |
| 正文里漏出反斜杠源码 | 0 处 | 0 处 |
| 整页被撑出横向滚动（`documentElement.scrollWidth`） | 否（1440/1440） | 否（390/390） |
| 超长块公式 | 内容 921px / 容器 752px | 内容 921px / 容器 350px |

#### 「长条、字变大、不换行」的三个真实来源

1. **块公式不会折行，容器也看不出还能滚动。** KaTeX 的公式是一个整体，没有断行点；
   `.ds-markdown-math.katex-display`（`src/components/markdown/markdown.css:223-230`）虽有
   `overflow-x: auto`，但滚动条在 Chrome/Safari 上默认隐藏、右侧也没有渐隐提示，
   于是超宽公式看上去就是**被右边缘硬切掉一截**。手机 390px 下尤其明显。
2. **公式确实比正文大一号。** `katex/dist/katex.min.css` 把 `.katex` 设为 `font-size: 1.21em`，
   正文 16px → 公式 19.4px。窄屏上一行又大又长的公式，正是用户描述的「字体变大不会换行」。
3. **矩阵/多列表这类结构天生超宽。** 14 列矩阵实测内容 921px，390px 手机上只能看到前 9 列
   （`swtest/shots/latex_wide_mobile.png`），且左右都没有提示。

#### 顺带实测到的两个真问题（与用户原话未必相关）

- **只有 3 类写法会让 KaTeX 抛错、回退成原始源码**（`src/components/markdown/MathFormula.tsx:43-45`
  走 fallback，把源码原样当正文显示）：`\label{}`、`\require{}`、`\hline` 用在 array 环境之外。
  Node 里用同一版 katex 0.18.2 逐条跑 32 个常见写法，只有这 3 条（外加把 `$` 当公式内容喂进去的
  1 条测试用例本身写错）报错；`\begin{equation}`、`\begin{align}`、`\bm`、`\tag`、`\text{中文}`、
  `\begin{cases}`、`\substack`、`\underbrace` 等在 0.18.2 里都能正常渲染。
  若后续确认用户看到的是「带反斜杠的原文」，就是这一类——修法是回退前先剔除 `\label`/`\require` 再试。
- **单美元会把货币吞掉**：`价格 $5 和 $10 不是公式` 渲染成「价格 `5 和` 10 不是公式」，
  两个 `$` 被当成定界符（`src/services/markdown/parse.ts:42` 的 `singleDollarTextMath: true`）。

### J. 已修：手机上一整晚的对话丢了（2026-11-22）

**症状**（用户原话概括）：聊了一夜加一早上，再打开「原来的对话框还有，以前聊的也都还有，
但昨天晚上和今天聊的都没有了」；没清缓存、没清浏览器数据；网页入口和主屏幕图标都找不着；
换分支也没找到。之后才导出备份，导出的包里同样没有这段。

**先纠正一个前提**：对话不在 localStorage，在 IndexedDB 的 `chat-demo` 库（`sessions` 正文 /
`sessionSummaries` 列表 / `files` 附件 / 两张导入暂存表，见 `src/services/chat/db.ts`）。
localStorage 只有 API Key 与设置开关。

**用 CDP 复现出来的三个缺口**（`swtest/probe_save_failure.py`，mock 一段 6 秒流式回答）：

| 缺口 | 实测 |
|---|---|
| 落盘窗口 = 一整轮回答 | 6 秒回答期间 `sessions.put` 只在发送时与收尾各一次，中间 6.1 秒零写入；真实回答两三分钟就是两三分钟窗口 |
| 写失败不硬停 | 让 `put` 抛 `QuotaExceededError`：顶部出现提示条，但输入框与发送照常可用，用户能继续聊几小时，而这期间每一轮都只存在内存里 |
| 失败不留证据 | 失败后刷新，`localStorage` 只有 `chat-demo:api-key`，没有任何记录，事后无法判断是配额满还是别的 |

**归因**：旧会话早已落盘所以安然无恙，从某个时刻 T 起写入失败（最可能是配额满）或页面被系统杀掉时
最后几次事务没提交，之后新建的一切都只在内存里 —— 这与「旧的全在、从某点起全没」完全吻合。
**整库被浏览器回收可以排除**：那种情况一条都不会剩。分支切换与此无关：分支只影响单条回答。

**修法**（P0+P1，2026-11-22）：

1. 流式期间按门槛落盘：距上次 ≥2 秒且内容涨了 8 千字符就写，最长 5 秒必写一次
   （`STREAM_SAVE_MIN_INTERVAL` / `STREAM_SAVE_MIN_CHARS` / `STREAM_SAVE_MAX_INTERVAL`）。
   实测 12 秒回答的最长相邻落盘间隔从「整段 12 秒」压到 5.2 秒。
2. 同一会话的保存串行化：在路上的那一笔没写完就只标脏，写完补一次，不再并发堆积。
3. 失败分流：`QuotaExceededError` 弹模态（`components/storage/SaveFailureDialog.tsx`），
   遮罩挡住输入框；其他错误仍走顶部提示条。出口已在 §8-M 重做（导出 / 去腾空间 / 继续聊，
   且配额失败立即停流），本节记的是最初那版。
4. 黑匣子：失败写 `localStorage` 的 `chat-demo:save-log`（环形 20 条，只记错误名与消息，不记对话内容）；
   下次打开若还有未处理/未确认的失败，顶部提示「上次有 N 条对话没能保存到本机」。

**验证**：`swtest/probe_durability.py` 五组全 PASS —— 流式中间库里已有本轮内容且最长间隔 5.2 秒；
配额满弹模态且输入框被遮罩盖住（`elementFromPoint` 命中 `overlay-*`）；`save-log` 有
`QuotaExceededError` 记录；刷新后出现「上次有 1 条…」提示、点「知道了」后刷新不再出现；
非配额错误不弹模态只走提示条。

**仍未做（留档，等下次同类反馈再决定）**：启动时把「正文有、列表摘要缺」的孤儿会话自动补回摘要。

### K. 新增：导入前逐条选择 + 空间预检（2026-11-22）

**背景**：官方只给「全部导出」，我们的导入也照抄了全有或全无——一次把几十 MB 塞进浏览器，
之后新建的对话没有余量写，第一条就撞配额。加上 §8-J 那个弹窗只是撞墙之后的事，用户在那一步
既不知道装了多少、也不知道还能装多少。

**行为**（`src/components/settings/ImportPicker.tsx`）：

- 选完 ZIP / 文件夹先扫归档，列出每条对话的标题、日期、消息数、体积；**默认一条都不选**
  （默认全选等于替用户做决定，空间很快就满）
- 排序默认按时间倒序，可切「按体积」——清理视角
- 工具条：全选 / 全不选 / 反选；底部实时显示「已选 N 条 · 约 X」
- 顶部两行：归档共多少条、约多大（含图片多少）+ 本机已用多少 / 上限约多少
- 选中体积超出剩余空间时确认按钮禁用，并折算成「还得再取消约 N 条」
- 语义不变：**全量替换**——勾上的进来，没勾的从本机消失；有旧记录时底部写明「会替换本机现有的 N 条」
- 缺少 `chat_session_index.json` 的归档**直接报「无法导入」**，不进入清单——导入层本来就要求索引齐全
  （`importArchive` 缺索引判 `backupIncomplete`），让用户确认一次再失败没有意义；
  索引列了会话、正文却一条都找不到的损坏归档同样在预览阶段就被拒（`previewArchive` 抛 `backupIncomplete`），
  不会出现一个勾不了任何东西的空清单

**实现要点**：

- 清单不解压任何会话：ZIP 中央目录里本来就有每条的**解压后大小**（`readDirectoryEntries`）；
  标题/时间/条数只读 `chat_session_index.json` 一个小条目（`readEntryByPath`）
- 导入时未勾选的会话与其图片**直接跳过、不解压**（`readArchive` 的 `skip`），
  否则为了忽略 90% 的内容仍要把整包解压一遍
- 预检口径改了：原来是「压缩包大小 ≤ 剩余」，现在按「**已用 + 这次要写的量 ≤ 上限**」——
  替换是「先写暂存、再原子换掉」，峰值是新旧同时存在（`commitStaging`）

**体积估算**（`estimateLocalBytes`）：`4 KB/条 + 0.7 × 文本字节 + 2.2 × 图片字节`。
系数是实测校准的（`swtest/probe_usage_calibration.py`、`probe_usage_big.py`、`probe_usage_many.py`）：

| 样本 | 归档字节 | 实测占用增量 | 模型值 |
|---|---|---|---|
| 110 条小会话（无图） | 212.6 KB 文本 | 537 KB | 4KB×110 + 0.7×212.6KB ≈ 589 KB |
| 10 条会话 + 10 张 20KB 图 | 32.7 KB 文本 / 200 KB 图 | 544 KB | 40 + 23 + 450 ≈ 513 KB |
| 120 条（含上面 10 张图） | 245 KB 文本 / 200 KB 图 | 1,082 KB | 480 + 172 + 450 ≈ 1,102 KB |
| 20 条 × 250 KB 长对话 | 5.13 MB 文本 | 3,458 KB | 80 + 3,592 ≈ 3,672 KB |

小会话由 IndexedDB 的记录粒度主导（两三条消息也被放大到 4 KB 上下），长会话由压缩比主导
（写进 IndexedDB 后约为原文的 0.6–0.7），图片在替换峰值时约为原字节的两倍。
**估算值只用于预告与拦截，不当作精确账**：真正写不进去时仍由配额错误兜底（导入是原子的，旧数据不变）。

**验证**：`swtest/probe_import_picker.py` 全 PASS——120 行清单、默认 0 选中、时间倒序、
全选/全不选/勾 20 条计数正确、导入后库里正好 20 条且只剩最近 20 条、附件只存选中的 10 张、
缺索引归档被拒且库内条数不变、空间不够时确认禁用并提示「还得再取消约 98 条」；
手机 375 宽（`shot_picker_mobile.py`）无横滚。
既有回归 `probe_import_guard.py`（坏归档被拒、旧历史保留）在改成清单后仍 PASS —— 它的导入步骤
已改为「先点全选再确认」，没有清单时直接读报错。

**未做**（留给下一轮）：撞墙后弹窗的出口改造（单条导出、文案说清
「导出包含未保存部分」、配额失败停流、`beforeunload`）。

### L. 新增：本机存储用量与低水位预警（2026-11-22）

**背景**：K 节让导入时可以挑，但用户仍然不知道「现在还剩多少」。§8-J 那个弹窗只在撞墙之后才出现，
在那之前界面里没有任何可看的数字；而撞墙那一刻，内存里还没落盘的内容就已经危险了。

**先把事实量清楚**（`swtest/probe_storage_quota.py`、`probe_quota_modes.py`，Chrome 158，
本机 C 盘 350 GB / 剩余 66.8 GB）：

| 量什么 | 实测 |
|---|---|
| `quota` | 10,737,427,837 B = **10.00 GiB**（有窗口与 headless 两次完全一致） |
| 空白应用 `usage` | 9,597 B（缓存 5,376 / IndexedDB 3,098 / SW 注册 1,123） |
| `usageDetails` | 有，能分出 `caches` / `indexedDB` / `serviceWorkerRegistrations` |
| `persisted()` / `persist()` | false / false（全新档案、没装成应用时浏览器不授予持久化） |

10 GiB 既不是磁盘的 60%（210 GB）也不是剩余空间的 60%（40 GB），所以它不是按磁盘算出来的；
具体是哪个常量没有查证。**这否掉了一种做法**：只做「配额用了 80% 就预警」的进度条——
一百条纯文本对话约 1 MB，桌面端要撞到 10 GiB 得聊十年，那条进度条永远不会亮。
真正吃空间的是附件（单图上限 64 MB、单条消息最多 20 个），所以这个数字必须能拆出附件占用。

**行为**（`src/components/settings/StorageRow.tsx` + `src/services/chat/storageInfo.ts`）：

- 设置「数据管理」第一行「本机存储」：`还能再存 X（已用 Y / 上限 Z）`
- 第二行体检：`N 条对话 · M 张附件（大小）· 最后写入 月-日`
- 第三行：浏览器会不会把本站列为持久存储（不会就说清「可能被自动清理，重要对话请另行备份」）
- 两档预警，阈值取「相对配额」与「绝对底线」中较小者（桌面 10 GiB、手机可能只有几百 MB，
  只用一个百分比两端都会失准）：
  - 黄：剩余 < min(200 MB, 配额 10%) → 本行左侧黄色色条 + 「空间不多了，建议先导出一份备份」
  - 红：剩余 < min(50 MB, 配额 2%) → 红色色条 + 聊天页顶部提示条（「先导出备份」/「知道了」）
- 「知道了」只压住当前这一轮：回到安全范围后再紧缺会重新出现；顶部条优先级低于
  §8-J 的「上次有 N 条没能保存」与配额模态弹性（那两条说的是已经发生的事，不该同时挂三条横幅）
- 浏览器给不出 `estimate()` 时只显示条数 / 附件 / 最后写入，不误报，也不留一行空白

**实现要点**：

- 「最后写入」读 IndexedDB 里的 `sessionSummaries`，不读内存里的会话状态——保存失败时内存照样前进，
  这个数字必须反映真正落盘的那一次，否则它恰好在最该报警的时候看不出问题
- 附件占用只读 Blob 的 `size` 与 base64 字符串长度，不解码原件
- `estimate()` 是跨进程调用：模块内缓存 + 30 秒节流；启动一次、回到页面一次、导入 / 导出 / 删除后强制重读；
  选完归档打开清单时也强制重读（马上要往里写，不能用旧值）
- 阈值只在 `storageInfo.storageLevel()` 一处，调数值只改那里
- 预警样式不用底色胶囊：黄 / 红放在左侧色条上，文字保持正文颜色（深色主题下也读得清）

**验证**：`swtest/probe_storage_row.py` 24 项全 PASS——充裕时显示 10.0 GB / 315 KB 且无预警；
黄（剩余 100 MB）只有黄条、没有顶部条；红（剩余 20 MB）出现顶部条并写明「还能再存 20 MB」；
点「知道了」后刷新不回来；回到充裕再变红会重新出现；`estimate()` 返回空时显示
「浏览器没有给出可用空间」且不误报；375 宽行内与页面都不横滚；深色主题下黄 / 红均可读；无页面报错。
回归：`probe_import_picker.py`、`probe_import_guard.py` 仍全 PASS。
截图：`storage_ok` / `storage_low` / `storage_critical` / `storage_unknown` / `storage_mobile` /
`storage_dark_low` / `storage_dark_critical`。

**未做**：撞墙后弹窗的其余两项——单条导出、按体积排序的清理面板（原因见 §8-M 末段；
出口改造、停流、`beforeunload` 已于同日做掉）。

### M. 新增：存不下时的救援弹窗（2026-11-22）

**背景**：J 节那个弹窗只把「悄悄丢」变成「看得见地丢」。读代码后发现三处硬伤：

1. **唯一的出口是「继续聊」**：`onClose` 是空函数、`closable` 没开，遮罩与 Esc 全部无效，
   想回到列表也没有按钮——不想丢内容的用户被关在这个框里。
2. **它不停流**：`acknowledgeSaveFailure` 只是把 `saveFailure` 置空，本轮生成继续跑；
   每 5 秒一次的进度落盘继续失败，`saveFailure` 又被置上，弹窗反复闪。
3. **文案指错了地方**：「删掉一些不需要的对话腾地方」——一条纯文本对话只有几十 KB，
   占空间的是附件（单图上限 64 MB），删对话腾不出多少。

**现在的三个出口**（`components/storage/SaveFailureDialog.tsx`）：

| 按钮 | 做什么 |
|---|---|
| 导出全部对话（主） | 打包 zip 下载；成功后正文里出现「已导出 deepseek_data-….zip」 |
| 去腾空间 | 关模态 + 回列表，侧边栏里删对话，删完接着聊 |
| 继续聊（不保存） | 关模态、留在原会话，行为同以前 |

「重试」去掉了：空间没变时重试必然失败，只会让模态再闪一次；真腾出空间后随手发一句就会重试落盘。

**配额失败立即停流**：`store.reportSaveFailure` 判定为配额错误时直接
`getStreamController(sessionId)?.abort()`，回答按「已停止」收尾（气泡下出现「继续生成」，之后可以接着写）。
不切的话，用户看得越多丢得越多。

**「导出包含未保存部分」是实测过的**：导出走内存里的 `sessionCache`（含尚未落盘的回复），不是只读 IndexedDB。
把写入开关关掉后流到第 26 段（共 60 段）失败，导出的 zip 里第 26 段齐全。

**离开前确认**：`bindChatPersistence` 增加 `beforeunload`，有未保存会话时 `preventDefault`；
浏览器只显示自己的固定文案，这里只决定拦不拦。这是不点弹窗直接关页面时的最后一道。

**「已导出」只对那一刻成立**：再次出现写失败时清掉那行（`useBackupExport.reset`），
否则用户会以为最新内容也存下来了，然后放心关页面。

**验证**：`swtest/probe_quota_rescue.py` 25 项全 PASS——模态标题与正文、三个按钮文案、停流后
不再变长且「停止生成」按钮消失、停在第 26/60 段、导出 zip 含未保存回答（1084 字节）、
「已导出 …zip」出现、继续聊留在原会话、去腾空间回列表、新的失败不再显示旧的「已导出」、
有未保存内容时拦离开 / 初始不拦、390 宽无横滚、深色可读、无页面报错；
另有一组反例：写入抛 `UnknownError` 时**不弹模态、不打断生成**（60 段全部收到）、只走顶部提示条——
停流只对配额满生效，别把它变成「任何写失败都掐断回答」。
截图：`quota_modal_light` / `quota_modal_exported` / `quota_modal_dark` / `quota_modal_mobile` / `quota_freed_list`。

**未做**：

- **单条导出**：现在只有整包。弹窗文案已说明「以后想恢复哪几条都可以挑」（K 节的勾选清单），
  整包 1 MB 级别、导入时能挑，先不为它加一条归档路径。
- **按体积排序的清理面板**：单条对话只有几十 KB，排序后每条都是 0.1 MB，删十条也腾不出 1 GB；
  真能回收空间的是清空历史，那是删除操作，留在设置「数据管理」里手动点，不进救援弹窗。
